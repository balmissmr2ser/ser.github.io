SERVICIOS DE CORREO EN LINUX

INTRODUCCIÓN

Un sistema de correo electrónico no es un único servicio, sino un conjunto de procesos que colaboran para aceptar mensajes, encaminarlos, almacenarlos y ponerlos a disposición del usuario final. En un despliegue clásico de Linux, lo habitual es separar al menos dos piezas:

  • Un servicio SMTP para el transporte y entrega entre servidores o clientes.
  • Un servicio IMAP/POP3 para que el usuario pueda consultar su buzón.

En esta unidad se trabajará con Postfix como servidor SMTP y con Dovecot como servidor de acceso a buzones. Es una combinación habitual en entornos Debian y Ubuntu porque ofrece una configuración razonablemente clara, buen rendimiento y una superficie de ataque moderada si se endurece de forma correcta.

ARQUITECTURA DEL SERVICIO DE CORREO

COMPONENTES PRINCIPALES

Componente Función Ejemplo en Linux
MTA Transfiere mensajes entre servidores y acepta correo entrante o saliente. Postfix
MDA Deposita el mensaje en el buzón del usuario. Dovecot LDA o entrega local de Postfix
MUA Cliente de correo usado por la persona usuaria. Thunderbird, Outlook, mutt
DNS Publica los registros necesarios para localizar el servidor de correo. Registros MX, A y PTR

PROTOCOLOS Y PUERTOS HABITUALES

Servicio Protocolo Puerto TCP Uso habitual
SMTP SMTP 25 Transporte entre servidores y recepción en el MTA
Submission SMTP autenticado 587 Envío de correo por clientes autenticados
SMTPS SMTP sobre TLS implícito 465 Compatibilidad con algunos clientes
POP3 POP3 110 Descarga de mensajes al cliente
POP3S POP3 sobre TLS 995 POP3 cifrado
IMAP IMAP 143 Acceso remoto sincronizado al buzón
IMAPS IMAP sobre TLS implícito 993 IMAP cifrado

En la práctica moderna, el acceso de clientes suele hacerse mediante submission 587 para el envío y IMAP 143/993 o POP3 110/995 para la lectura. El puerto 25 se reserva principalmente para comunicaciones entre MTAs.

REQUISITOS PREVIOS

IDENTIDAD DEL SERVIDOR

Antes de instalar los servicios conviene fijar correctamente el nombre del sistema. Un servidor de correo debe tener un nombre coherente y resoluble, por ejemplo mail.ser.smr.

hostnamectl set-hostname mail.ser.smr

Además, /etc/hosts debe incluir al menos una resolución local coherente para el propio servidor:

127.0.0.1       localhost
192.168.1.201   mail.ser.smr mail

DNS NECESARIO

Para que otros sistemas localicen el servidor de correo del dominio hacen falta, como mínimo, estos registros:

ser.smr.        IN MX 10 mail.ser.smr.
mail.ser.smr.   IN A  192.168.1.201
201.1.168.192.in-addr.arpa. IN PTR mail.ser.smr.

Sin un registro MX correcto, los MTAs remotos no sabrán a qué servidor deben entregar el correo del dominio. Sin resolución A y PTR coherente es frecuente que aparezcan rechazos o puntuaciones negativas por filtros antispam.

INSTALACIÓN DE POSTFIX Y DOVECOT

PAQUETES BÁSICOS

apt update
apt install postfix dovecot-core dovecot-imapd mailutils

Durante la instalación de Postfix en Debian suele aparecer un asistente. Para un laboratorio sencillo se puede elegir Internet Site e indicar como nombre del sistema mail.ser.smr.

COMPROBACIÓN DE SERVICIOS

systemctl status postfix
systemctl status dovecot
ss -ltnp | egrep ':(25|143) '

Archivo Función

CONFIGURACIÓN BÁSICA EN MAIN.CF

Una configuración inicial razonable para un servidor del dominio ser.smr con buzones locales en formato Maildir puede ser la siguiente:

myhostname = mail.ser.smr
mydomain = ser.smr
myorigin = $mydomain
inet_interfaces = all
inet_protocols = ipv4
mydestination = $myhostname, localhost.$mydomain, localhost, $mydomain
mynetworks = 127.0.0.0/8, 192.168.1.0/24
home_mailbox = Maildir/
smtpd_banner = $myhostname ESMTP
append_dot_mydomain = no
recipient_delimiter = +
relayhost =
smtpd_relay_restrictions = permit_mynetworks, reject_unauth_destination
alias_maps = hash:/etc/aliases
alias_database = hash:/etc/aliases

Los puntos más importantes de esta configuración son los siguientes:

  • myhostname identifica al servidor SMTP.
  • mydestination define para qué dominios el servidor es destino final, es decir, dónde reparte el correo localmente.
  • mynetworks indica qué redes pueden usar el servidor como relay sin autenticación. Debe ser muy restrictivo.
  • home_mailbox = Maildir/ hace que cada usuario guarde sus mensajes en ~/Maildir.
  • reject_unauth_destination evita convertir el servidor en un open relay.

DOVECOT

OBJETIVO DE DOVECOT

Dovecot se encarga de que los clientes puedan leer y gestionar sus buzones mediante IMAP. También puede participar en la autenticación SMTP y en la entrega local, aunque para un escenario básico es suficiente con usarlo como servidor de acceso a buzones.

CONFIGURACIÓN MÍNIMA

En Debian y Ubuntu la configuración se reparte entre varios ficheros dentro de /etc/dovecot/conf.d/. Para esta fase solo interesa que Dovecot encuentre los buzones Maildir y escuche en IMAP sin añadir todavía ni TLS ni autenticación SASL para Postfix.

MAILDIR

# /etc/dovecot/conf.d/10-mail.conf
mail_location = maildir:~/Maildir

PROTOCOLOS HABILITADOS

# /etc/dovecot/dovecot.conf
protocols = imap

AUTENTICACIÓN EN ESTA FASE

# /etc/dovecot/conf.d/10-auth.conf
disable_plaintext_auth = no
auth_mechanisms = plain login

Como todavía no se ha configurado TLS, la directiva disable_plaintext_auth = no permite hacer pruebas de laboratorio con autenticación en claro sobre IMAP. Esto solo es aceptable en un entorno aislado de prácticas.

COMPROBAR LA CONFIGURACIÓN ACTIVA

doveconf -n
systemctl restart dovecot
systemctl status dovecot
ss -ltnp | egrep ':(143) '

Si todo es correcto, Dovecot debería quedar escuchando en el puerto 143 para IMAP. Los puertos 993 y 587 no son necesarios todavía en esta fase.

ESCENARIO PRÁCTICO: SERVIDOR CON USUARIOS LOCALES

CREACIÓN DE USUARIOS

adduser admin
adduser alumno1
adduser alumno2

CREACIÓN DE BUZONES MAILDIR

Si el buzón aún no existe, se puede crear el árbol Maildir desde cada cuenta o con la utilidad de Dovecot.

doveadm mailbox create -u admin INBOX
doveadm mailbox create -u alumno1 INBOX
doveadm mailbox create -u alumno2 INBOX

Otra posibilidad es generar ~/Maildir enviando el primer mensaje local una vez configurado home_mailbox = Maildir/.

ENVÍO DE PRUEBA LOCAL

echo "Prueba de correo local" | mail -s "mensaje 01" alumno1
echo "Segundo mensaje para comprobar lectura por IMAP" | mail -s "mensaje 02" alumno1

REVISIÓN DE REGISTROS

tail -f /var/log/mail.log

COMPROBACIÓN DE COLA

mailq
postqueue -p

PRUEBAS DE FUNCIONAMIENTO

PRUEBA SMTP EN BRUTO

telnet mail.ser.smr 25
EHLO cliente.ser.smr
MAIL FROM:<admin@ser.smr>
RCPT TO:<alumno1@ser.smr>
DATA
Subject: prueba smtp

Mensaje enviado manualmente.
.
QUIT

PRUEBA IMAP EN TEXTO CLARO

telnet mail.ser.smr 143
a login alumno1 su_clave
a select inbox
a fetch 1 body[header.fields (subject from to date)]
a fetch 1 body[text]
a logout

Si la autenticación es correcta, el servidor responderá con líneas OK y mostrará el contenido del mensaje almacenado en INBOX. Con select inbox se abre el buzón y con fetch se recuperan cabeceras o cuerpo.

COMPROBACIÓN DIRECTA DEL MAILDIR

ls -R /home/alumno1/Maildir
find /home/alumno1/Maildir/new /home/alumno1/Maildir/cur -type f
sudo -u alumno1 mail

Además de IMAP, se puede confirmar que Postfix ha depositado los mensajes en el buzón local inspeccionando Maildir o leyendo el correo con la utilidad de consola mail desde la cuenta del usuario.

CONTINUACIÓN DE LA PRÁCTICA: PROBAR DOVECOT

Partiendo de una práctica como la descrita, en la que Postfix ya entrega el correo localmente en formato Maildir/, el siguiente paso consiste en activar Dovecot para que los usuarios puedan leer sus mensajes mediante IMAP. En este escenario se sigue trabajando sin cifrado TLS y sin autenticación SASL en Postfix.

INSTALACIÓN DE DOVECOT

apt update
apt install dovecot-core dovecot-imapd
systemctl enable dovecot.service
systemctl restart dovecot.service
systemctl status dovecot.service

CONFIGURACIÓN DE DOVECOT PARA MAILDIR

Como en la práctica previa ya se ha cambiado Postfix a home_mailbox = Maildir/, Dovecot debe apuntar a ese mismo formato de buzón. Para esta fase interesa únicamente permitir acceso a buzones locales por IMAP en texto claro dentro de la red de laboratorio.

sed -i 's|^mail_location =.*|mail_location = maildir:~/Maildir|' /etc/dovecot/conf.d/10-mail.conf
sed -i 's|^#\?disable_plaintext_auth =.*|disable_plaintext_auth = no|' /etc/dovecot/conf.d/10-auth.conf
sed -i 's|^#\?auth_mechanisms =.*|auth_mechanisms = plain login|' /etc/dovecot/conf.d/10-auth.conf
sed -i 's|^#\?protocols =.*|protocols = imap|' /etc/dovecot/dovecot.conf

Una vez ajustados estos parámetros se puede revisar la configuración efectiva y reiniciar el servicio.

doveconf -n
systemctl restart dovecot.service
systemctl status dovecot.service
ss -ltnp | egrep ':(143) '

Si la configuración es correcta, Dovecot quedará escuchando en 0.0.0.0:143 para IMAP. En esta fase no debe aparecer todavía 993 porque no se ha activado TLS.

COMPROBAR QUE U1 TIENE MENSAJES EN MAILDIR

tree /home/correo/u1/Maildir
ls -l /home/correo/u1/Maildir/new

Antes de probar IMAP conviene verificar que el buzón de u1 ya contiene mensajes depositados por Postfix. Si en Maildir/new aparecen ficheros, Dovecot debería poder listarlos y entregarlos al cliente.

LECTURA MÁS CÓMODA CON S-NAIL

Para esta práctica, la forma recomendada de comprobar la lectura del correo será s-nail, la misma utilidad que ya se empleó para enviar mensajes. Como s-nail puede abrir un buzón remoto IMAP, resulta una manera mucho más cómoda de verificar que Dovecot entrega correctamente los correos.

LEER EL BUZÓN POR IMAP

mail -f 'imap://u1@172.16.1.6/INBOX'

Con IMAP se accede al buzón INBOX manteniendo una visión más cercana a la estructura real del servidor. Las órdenes interactivas más útiles siguen siendo las mismas:

headers
type 1
Type 2
z
quit

El comando Type muestra el mensaje con más cabeceras y partes MIME visibles, algo útil cuando se quiere comprobar que un adjunto como mailserver.png ha llegado y aparece codificado en base64.

OBSERVACIÓN PRÁCTICA

  • Para no dejar la contraseña escrita en el historial, es mejor usar imap://u1@172.16.1.6/INBOX sin incluir la clave en la propia URL.
  • Para no dejar la contraseña escrita en el historial, es mejor usar imap://u1@172.16.1.6/INBOX sin incluir la clave en la propia URL.
  • Aunque el acceso sea más cómodo que con telnet, en esta fase sigue siendo tráfico sin cifrar, por lo que solo debe usarse dentro de la red de prácticas.
  • Si s-nail muestra el listado de mensajes y permite abrirlos, queda validado que Dovecot está sirviendo correctamente el buzón remoto.
  • Las pruebas con telnet pueden dejarse como comprobación técnica adicional para ver directamente el diálogo IMAP, pero ya no son la vía principal de validación.

COMPROBACIÓN TÉCNICA DEL PROTOCOLO IMAP

Si se quiere ver el intercambio de órdenes y respuestas a bajo nivel, desde L02C00-Alpine puede hacerse una comprobación simple conectando al puerto 143 del servidor. Si no se dispone de telnet, se puede usar nc.

telnet 172.16.1.6 143
* OK [CAPABILITY IMAP4rev1 SASL-IR LOGIN-REFERRALS ID ENABLE IDLE LITERAL+] Dovecot ready.
a login u1 clave_de_u1
a select inbox
a fetch 1 body[header.fields (from to subject date)]
a fetch 1 body[text]
a logout

La respuesta esperada incluye líneas OK tras login y select, además del contenido del mensaje al ejecutar fetch. Si el mensaje tenía adjuntos, con esta comprobación se visualizan al menos sus cabeceras MIME y el texto del mensaje.

COMPROBACIÓN EN EL LOG DEL SERVIDOR

tail -n 50 /var/log/mail.log
... dovecot: imap-login: Login: user=<u1>, method=PLAIN, rip=172.16.2.236, lip=172.16.1.6, mpid=...
... dovecot: imap(u1): Disconnected: Logged out bytes=.../...

Estas líneas confirman que el acceso al buzón ya no lo hace Postfix, sino Dovecot. Postfix sigue encargándose de recibir y entregar el mensaje en Maildir/, mientras que Dovecot se ocupa de presentarlo al cliente mediante IMAP.

INTERPRETACIÓN DEL RESULTADO

  • Si login funciona pero select inbox no muestra mensajes, el problema suele estar en la ubicación del buzón o en permisos sobre Maildir/.
  • Si Dovecot no escucha en 143, conviene revisar doveconf -n y el estado del servicio.
  • Si s-nail abre el buzón y permite leer mensajes, la validación funcional de Dovecot puede darse por correcta.
  • Si aparece el texto del mensaje y también los bloques Content-Type o Content-Transfer-Encoding: base64, queda demostrado que el cliente está accediendo al mismo mensaje ya depositado previamente por Postfix.

Más adelante podrá montarse un segundo servidor dedicado a POP3, pero en esta práctica conviene dejar claro que este servidor queda orientado solo a IMAP.

PRUEBA DNS

dig mx ser.smr
dig a mail.ser.smr
dig -x 192.168.1.201

SEGURIDAD Y ENDURECIMIENTO

  • No permitir relay abierto. La directiva crítica es reject_unauth_destination.
  • Mientras no exista TLS, no exponer IMAP fuera de la red de prácticas.
  • Posponer submission 587 y la autenticación SASL hasta la siguiente fase de endurecimiento.
  • Usar TLS en SMTP e IMAP en cuanto la práctica avance a la fase segura.
  • Limitar con firewall los puertos realmente necesarios.
  • Revisar de forma periódica /var/log/mail.log para detectar errores de autenticación, colas bloqueadas o rechazos por DNS.
  • Asegurar coherencia entre hostname, registros A, MX y PTR.
  • Evitar cuentas sin contraseña y deshabilitar accesos innecesarios.

RESUMEN OPERATIVO

apt install postfix dovecot-core dovecot-imapd mailutils
postfix check
systemctl restart postfix dovecot
postconf -n
doveconf -n
ss -ltnp | egrep ':(25|143) '
tail -f /var/log/mail.log

Con esta base ya se dispone de un servidor de correo funcional para un entorno de laboratorio: Postfix recibe y entrega mensajes del dominio, Dovecot ofrece acceso a los buzones en texto claro mediante IMAP y el sistema puede validarse mediante pruebas SMTP, IMAP y consultas DNS. El siguiente paso natural será endurecer el servicio activando TLS y, si hace falta envío autenticado para clientes, integrar también SASL.
